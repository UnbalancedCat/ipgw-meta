# ADR-0016：CAS 来源诊断先于选键语义变更

本记录为离线设计提案，不替代已接受的协议、安全或发布约定，不授权网络操作。产品仍遵循 [PROTO-DISCOVERY-001](../protocol-correctness.md)、[ADR-0014](ADR-0014-cas-rsa-compatibility-envelope.md) 和 [ADR-0015](ADR-0015-cas-submit-closed-fields.md)。本提案没有决定哪把真实公钥正确。

2026-10-29 导航补充：本提案保持 proposed，以下设计与历史结论保留；当前执行优先级以[认证收敛 roadmap](../../upgrade/plan.md#roadmap-20261029)为准。先比较旧版与 v1 的行为，按具体认证假设安排最小观测；不把完成独立诊断的全部覆盖或 D4–D15 的 CTL 研究作为产品修复前置。涉及取键语义的后续决策仍须证据、规范及回归支持。

## 背景与已知证据

历史交接说明 CAS-submit 诊断收到 HTTP 500，真实登录闭环未完成；后续匿名诊断观察到两个不同的 publicKeyStr，已排除该窗口中的“通用 publicKey 抢先匹配”假设。这些是交接支持的历史事实，不是本窗口重新读取真实响应的结果。

独立合成观察表明：internal/cas/page.go 在整个输入字节上做大小写不敏感的首次正则匹配；auth.go 在页面已匹配时不读取外部脚本，否则只考虑同源且路径含 login/rsa 的脚本，首次匹配后短路。调换候选顺序会改变选择。文本匹配不足以证明 JavaScript 中的赋值、作用域、实际调用顺序或用于 rsa 字段的密钥。

历史 R2 原包本身已含 runner/EXE 绑定错误，其 self-test 仅直接执行 EXE，未覆盖完整 runner 校验链。新开发工具需要重新建立源码与产物身份，不能修补已安装历史文件后称为原 R2。

## 提议的诊断边界

1. 建立独立维护者诊断工具，第一阶段仅支持内建合成场景与整链 self-test，不包含真实采集入口。它不依赖 SDK.Login、CredentialProvider、profile、keyring、认证 POST、activation 或 logout。现有 cas-observe 是调用 SDK 的纯合成比较器，不作为未来匿名采集 runner。
2. 分别报告原始匹配、受支持语法中的候选赋值、可证明的有限静态使用关系。只收集事实，不输出 selected_key 或 correct_key。未支持的语法、跨函数数据流、动态执行顺序和遮蔽关系必须明确 unknown；不能把未识别计为不存在。
3. 诊断中的多键是观测结果，不自动转为产品拒绝规则。相同键重复、不同键和来源顺序都需要保留。页面/脚本读取顺序与运行时执行顺序分别表示，不把 DOM 顺序当实际执行证明。
4. 公钥仅在内存中解析和比较，使用本轮局部标签表达相等关系；不输出 key bytes、持久指纹、原始脚本、URL、表单值或原始错误。规则见 [SEC-SECRET-001](../security.md)、[SEC-LOG-001](../security.md) 和 [EVID-REDACT-001](../../evidence/README.md)。
5. runner、EXE、构建输入、manifest 和可信外部期望值构成完整绑定链；自洽哈希清单不等于来源证明。安装自测必须通过真实 runner 的验证路径，并在失败时证明尚未启动 EXE、网络或 profile 操作。详细草案见 [REL-CAS-DIAG-001](../../operations/cas-provenance-diagnostic.md)。

## 暂不采纳的策略

| 策略 | 当前不足 |
|---|---|
| 固定首个或第二个候选 | 无真实使用关系证明；顺序会变 |
| 遇到任何多键一律拒绝 | 相同键重复及未参与认证的键可能合法；这是新产品语义 |
| 仅补正则边界便认定根因解决 | 无法解释注释、字符串、作用域、动态赋值和最终使用关系 |
| 执行页面 JavaScript 获得答案 | 引入不可信代码执行与浏览器会话面，不属于本工具边界 |
| 复用 SDK.Login 并拦截 POST | 采集路径仍包含凭据/会话副作用；无法构成零凭据架构边界 |
| 固定旧公钥或修改旧 R2 安装 | 破坏动态发现和历史产物身份 |

## 产品选键决策的进入条件

在改变公共行为之前，至少需要：可复核的匿名来源分类、赋值到加密调用之间的关系证据、歧义和未支持语法的明确处置、对应合成回归，以及更新协议规范的评审结论。匿名来源观察仍不能证明服务端接受某键或登录成功；正式验证继续遵循 [PROTO-LOGIN-001](../protocol-correctness.md)。

本记录保留 proposed。离线诊断设计可先实施验证，但不因 self-test 通过自动提升为已接受的选键规则。下一次决策应明确选择解析覆盖范围与产品遇到不确定关系时的行为，而不是从这份提案推断“首键正确”或“多键必须拒绝”。
